# 每週時間看板：資料表設計提案

**狀態：等使用者核可，還沒開工。** 核可之後才寫 migration。

---

## 1. 兩張表

```sql
-- 每個人「每週固定有空」的半小時格子。
-- weekday / minute 是**這個人自己時區**的星期與時刻（規格 §5-1），
-- 解讀它們要靠 profiles.tz。不存 UTC、不存偏移量。
create table public.availability (
  user_id uuid not null references public.profiles(id) on delete cascade,
  weekday smallint not null check (weekday between 0 and 6),
  minute  smallint not null check (minute >= 0 and minute < 1440 and minute % 30 = 0),
  primary key (user_id, weekday, minute)
);

-- 每個幹部一列。「上次更新」與「看過告知了沒」。
create table public.availability_meta (
  user_id        uuid primary key references public.profiles(id) on delete cascade,
  updated_at     timestamptz not null default now(),
  notice_seen_at timestamptz
);
```

### 為什麼是「一格一列」，不是區間、也不是 bitmap

看板的核心查詢是「這一格有誰有空」。一格一列的話那是最單純的分組；
存區間的話每次編輯都要合併與切割，而算重疊要範圍邏輯。
存 336 個 bit 的 bitmap 只有一列，但 SQL 就完全查不動，
而且規格 §4-4 要求預留擴充空間，bitmap 是最難擴充的形狀。

**量級不是問題**：三十個人各填 20 小時 = 40 格，全部約 1200 列。
整張表一次讀回來也才 1200 列，不需要任何額外索引（主鍵夠了）。
**不要為了「以後可能會查」先加索引** —— 現在沒有那個查詢。

### 為什麼沒有代理主鍵 id

`(user_id, weekday, minute)` 本身就是身分。少一個欄位，而且
`insert ... on conflict do nothing` 天然冪等 —— 手滑連點兩下不會變成兩列。
（跟 `claim_invite` 那個 `for update` 是同一種考量。）

### 為什麼 minute 存分鐘，不是 0–47 的格子編號

規格 §5-1 的例子就是 `{weekday: 1, minute: 1140}`。
而且「分鐘」以後要改成 15 分鐘一格只要放寬那個 `% 30`，
欄位的意思不變；存格子編號的話 0–47 會變成 0–95，舊資料整批要換算。

### weekday 的 0 是星期日

跟 JavaScript 的 `Date.getDay()` 一致（0=日、1=一）。
**這一條要寫進欄位註解。** ISO 8601 是 1=星期一，兩套差一天，
而差一天的 bug 在畫面上看起來只是「這個人的時間怪怪的」。
看板欄位要顯示成週一到週日是畫面的事，不是儲存的事。

## 2. 權限：讀和寫兩端都認 cadre

```sql
alter table public.availability      enable row level security;
alter table public.availability_meta enable row level security;

-- 讀：只有登入的幹部。學員與未登入的人一列都讀不到。
create policy availability_read on public.availability
  for select using (public.is_cadre());

-- 寫：只能寫自己的，而且必須是幹部。
create policy availability_insert on public.availability
  for insert with check (auth.uid() = user_id and public.is_cadre());
create policy availability_delete on public.availability
  for delete using (auth.uid() = user_id and public.is_cadre());

create policy meta_read on public.availability_meta
  for select using (public.is_cadre());
create policy meta_insert on public.availability_meta
  for insert with check (auth.uid() = user_id and public.is_cadre());
create policy meta_update on public.availability_meta
  for update using (auth.uid() = user_id and public.is_cadre())
              with check (auth.uid() = user_id and public.is_cadre());

-- ⚠ 授權跟政策是兩件事，兩件都要做。
-- 2026-09-01 咬過一次：profiles 少 grant 一個欄位，三個寫入路徑全部靜靜地壞掉，
-- 而 RLS 政策是對的、兩層驗收也都真的通過了。
grant select, insert, delete on public.availability      to authenticated;
grant select, insert         on public.availability_meta to authenticated;
grant update (notice_seen_at) on public.availability_meta to authenticated;
```

### availability 刻意沒有 update

那張表除了主鍵沒有別的欄位，「改時間」就是刪掉舊格子、插入新格子。
沒有 update 政策也沒有 update 授權，等於「改到別人的列」這個 bug class
在這張表上不存在。以後真的加了欄位，update 會直接失敗 —— 大聲壞掉，
比安靜地放行好。

### updated_at 不給前端寫

`grant update` 只給了 `notice_seen_at`。`updated_at` 由 trigger 維護：

```sql
create or replace function public.touch_availability()
returns trigger language plpgsql security definer
set search_path = public, pg_temp as $$
begin
  insert into availability_meta (user_id, updated_at)
  values (coalesce(new.user_id, old.user_id), now())
  on conflict (user_id) do update set updated_at = now();
  return coalesce(new, old);
end $$;

create trigger availability_touch
after insert or delete on public.availability
for each row execute function public.touch_availability();
```

**理由是這個欄位的用途。** 規格 §4-3 C 用它做「超過 30 天標紅」，
那是拿來催人的。前端寫得動的話，一個 bug（或一個不想被催的人）
就能讓自己永遠是綠的，而看板會顯示得很正常。

## 3. 時區：解讀所有格子的鑰匙是 profiles.tz

`weekday`/`minute` 沒有 `profiles.tz` 就沒有意義。現況：那個欄位是 text、
可為 null，而且**目前兩個帳號都是 null**。

### 不設預設值

`not null default 'Asia/Taipei'` 看起來省事，但那是**用一個猜測填掉一個空格**：
一個在密西根的人會被安靜地畫到台北的時間上，而畫面看起來完全正常 ——
沒有人看得出來那是錯的。空值至少誠實。

### 沒填時區的人怎麼處理

不加資料庫約束（跨表的 check 要 trigger，不值得）。改成：

- 編輯自己的時間之前，先要他設時區；沒設就不讓他填
- 看板**不畫**時區為 null 的人的格子（畫不出來）
- 但成員清單裡**要出現他**，標成「還沒設定時區」

第三點是關鍵：直接把他濾掉的話，看板看起來完整而正確，
而少了一個人這件事沒有任何地方會講。

### 改時區的語意

改時區之後，所有格子照新時區重新解讀 ——「每週一 19:00」搬到美國之後
仍然是當地的週一 19:00。這是對的（多數人的「有空」是綁作息不是綁絕對時刻），
但**改的時候畫面要講**，不然搬家的人不會知道自己的時間全部變了。

### 別名表放在前端，不進資料庫

規格 §5-4 要一份中文與地名別名表（打「密西根」「安娜堡」都要找得到）。
那是搜尋用的常數，不是資料，放在 `availability/src/tz-alias.js`。
**加一條守門**：`destinations` 那 24 個城市每一個都要在別名表裡有對應，
少一個就紅。那 24 個就是 BT 的人真的在的地方，而小城市正是使用者
最猜不到自己該選哪個 IANA 時區的情況。

## 4. §4-4 的擴充空間怎麼留

「這週三我要考試」這一版不做。留的方式是**什麼都不做**：

以後加一張 `availability_exceptions (user_id, on_date, minute, available boolean)`
就行，現在這兩張表一個字都不用改。

**現在不要先加一個可為 null 的 `on_date` 進主鍵。** 那會讓現在這張表的
主鍵語意變模糊（null 在主鍵裡本來就不能用），而且「預留欄位」通常的下場是
放了三年沒人用，然後沒有人敢刪。

## 5. 要先講清楚的事：這個功能本身就是把作息表發給所有幹部

看板要顯示「誰有空、誰沒空」，而時區換算要在**觀看者**的瀏覽器裡做，
所以每個幹部的瀏覽器都會拿到**全部三十個人的完整作息表**。

這是功能本身的形狀，不是實作偷懶 —— 沒有辦法「只給他看得到的部分」，
因為看板就是要給他看。RLS 能做的是把這件事限制在 `role = 'cadre'`，
不能讓它變成更少。

所以規格 §4-5 第 3 點那句告知不是禮貌，是這個功能唯一的知情同意：
**「你填的每週時間，其他 BT 幹部看得到。」** 第一次進去就要看到，
`notice_seen_at` 存的就是這件事。

## 6. 三個要你決定的問題

### Q1. 「我確認過了，沒有變」要不要做

規格 §4-3 C 是「上次更新超過 30 天標紅」。但作息穩定的人**本來就不需要改**，
他會永遠紅著，然後被一直催 —— 催到後來大家就不信任那個紅色了。

**建議做一顆「確認沒變」**，按了就更新 `updated_at`。
成本是一顆按鈕加一支 RPC（因為 `updated_at` 前端寫不動）。

不做的話，紅色的意思會從「這個人的資料可能過期」變成
「這個人最近沒有動過」，而看板要問的是前者。

### Q2. availability_meta 要不要併進 profiles

併進去：少一張表，`profiles` 本來就一人一列。
不併：看板的東西全部在看板自己的兩張表裡，
權限、刪除、驗收都只看一組政策；`profiles` 是護照的進度牆也在讀的表。

**建議不併。**

### Q3. 表名

提案用 `availability` / `availability_meta`，跟資料夾 `availability/` 一致
（規格 §2-1）。

## 7. 核可之後的順序

1. migration（建表、政策、授權、trigger）
2. 驗收 SQL：用真實的 token 驗「學員讀不到」「改不了別人的」，
   **含正向對照組** —— 沒有它，全綠證明的只是「什麼都讀不到」
3. 反向驗證：把每一條政策各弄壞一次，確認驗收真的變紅
